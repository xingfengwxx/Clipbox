# 派单与提示词指南

## 核心原则

1. **上下文在仓库里，提示词只做指针。** 不要把手写的需求、表结构、接口字段塞进提示词；让 Agent 读 `AGENTS.md` 和任务卡。
2. **一张卡一次派单。** 不要把多张卡合并成一次「大任务」；单 Agent 串行时尤其如此。
3. **验收命令必须写进提示词吗？** 不必。任务卡里已有；提示词只需要求「逐条执行任务卡验收并粘贴证据」。
4. **发现冲突就停。** 文档之间不一致、依赖缺失、验收无法执行时，要求 Agent 停下汇报，不允许自行改契约或降标准。
5. **一卡一提交。** 提交信息 `T-XX: <一句话>`；不 push，不打 tag，除非该卡明确要求。

## 开工执行卡模板

> 复制下面整段，替换 `<任务卡编号>`、`<任务卡文件>`、`<一句话目标>`。

```text
你是 Clipbox 项目的实现 Agent。仓库根目录：/Users/wangxingxing/AndroidStudioProjects/MyProjects/Clipbox

本次只执行一张任务卡：<任务卡编号>，定义在 docs/tasks/<任务卡文件>。

步骤：
1. 先读 AGENTS.md，再完整读这张任务卡及其「必读」列出的文档章节。
2. 用 3–5 条列出你的实施计划，确认前置条件已满足、涉及路径明确。
3. 只修改任务卡「涉及路径」内的文件；按「实现要点」实现，不做额外功能。
4. 逐条执行「验收」命令，保留真实输出；失败则修复后重跑，不允许跳过。
5. 通过后按统一 DoD 自检，然后 git add 指定文件并提交：`<任务卡编号>: <一句话目标>`。
6. 最后汇报：改了哪些文件、验收命令与结果、提交哈希、遗留风险。

约束：
- 不修改 docs/ 下已冻结的需求、接口与架构文档；发现文档冲突立即停下说明。
- 不升级依赖、不引入新框架、不做任务卡「禁止」中的事。
- 不 push、不打 tag、不开始下一张卡。
```

## 验收失败修复模板

> 用于同一张卡验收未通过时。不要重发整张开工提示词，也不要让 Agent「再试试」。

```text
继续处理 <任务卡编号>，本次只做验收失败修复。

失败命令：
<粘贴命令>

实际输出：
<粘贴关键输出，完整堆栈可放最后>

期望结果：
<任务卡中的预期>

要求：
1. 先定位根因，用一段话说明为什么会失败；不要先改代码。
2. 只修复与该失败相关的最小范围；不重构、不改契约、不扩大范围。
3. 修复后重跑原命令与任务卡全部验收命令，粘贴结果。
4. 若根因涉及文档冲突或前置卡缺陷，停下汇报，不要自行绕过。
5. 通过后创建新提交（不要 amend 旧提交），提交信息：`<任务卡编号>: fix <简述>`。
```

最多两轮修复。两轮仍失败，停止该卡，人工介入。

## 示例：第一张卡的完整提示词

```text
你是 Clipbox 项目的实现 Agent。仓库根目录：/Users/wangxingxing/AndroidStudioProjects/MyProjects/Clipbox

本次只执行 T-S-01，任务卡在 docs/tasks/01-server.md。

先读 AGENTS.md，再读 T-S-01 及其必读章节。用 3–5 条列出计划后开始实现。只改任务卡涉及路径，不做配对、数据库或 Docker。完成后逐条跑验收命令并粘贴输出，按 DoD 自检，提交 `T-S-01: 服务端骨架与配置校验`。

不修改冻结文档，不升级依赖，不 push，不做下一张卡。
```

对应任务卡：`docs/tasks/01-server.md` 的「T-S-01 服务端工程骨架与配置校验」。

## 用户动作卡怎么派

T-IOS-01、T-REL-01 需要用户本人操作（安装 Xcode、准备服务器）。派单方式：

```text
读取 docs/tasks/04-ios.md 的 T-IOS-01。不要执行安装命令，只输出：
1. 我需要执行的完整命令清单；
2. 每一步的预期输出；
3. 我执行完后，你用哪些命令复核；
4. 失败时分别怎么处理。

等我贴回输出后，你再复核并提交该卡的记录。
```

Agent 在用户确认前不得尝试 `sudo`、安装软件或修改系统配置。

## 派单后的检查清单

每张卡完成后，人工检查：

- [ ] 提交信息符合 `T-XX: ...`，且只有一个提交。
- [ ] `git show --stat` 只包含任务卡涉及路径。
- [ ] 验收命令的真实输出已粘贴，不是「应该可以」。
- [ ] 没有新增 `TODO`、调试日志、注释掉的代码。
- [ ] 没有修改冻结文档或降低验收标准。
- [ ] 下一张卡的前置已满足。

## 什么时候不要派下一张卡

- 当前卡验收失败且修复未闭环。
- 当前卡引入了未记录的偏差（依赖版本、接口字段、目录结构）。
- 当前卡修改了任务卡「禁止」列表中的内容。
- 文档冲突尚未裁决。

## 里程碑 Gate

到达 M1 / M2 / M3 / M4 时，先跑 Gate 验收（见 `docs/tasks/README.md` §2），再打里程碑 tag：

```bash
git tag -a m1-minimal-loop -m "M1: minimal sync loop"
```

Gate 未通过不得进入下一里程碑。tag 是否 push 由用户确认。
