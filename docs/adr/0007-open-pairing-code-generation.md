# 配对码对所有设备开放，未配对设备可自助取码

**Status**: accepted

**Date**: 2026-11-19

## Context

ADR-0006 把取码改造为「已配对设备生成」，接口 `POST /api/v1/devices/me/pairing-code` 强制设备 Bearer 认证，客户端设置页也只对已配对设备展示入口。实际使用中，用户反馈这个判断不对：尚未配对、或刚安装还未配置服务器的设备无法主动取码，与「每台设备都可以生成配对码」的产品预期不符。

2026-11-19 用户明确决策：所有设备（含未配对）都可以生成配对码，并接受由此带来的自助注册范围扩大。本 ADR 部分取代 ADR-0006 中「只有已配对设备可以生成配对码」的认证要求；TTL、单活码、哈希存储、`/bootstrap` 与 `/pair` 语义保持不变。

## Decision

- `POST /api/v1/devices/me/pairing-code` 改为可选设备认证：
  - 未携带 `Authorization`：以匿名身份签发配对码，落入固定 issuer 槽位 `anonymous`。
  - 携带有效设备令牌：码归属该设备，与 ADR-0006 一致。
  - 携带无效或畸形凭证：返回 401 `UNAUTHORIZED`，不静默降级为匿名。
- 迁移 `V003__pairing_code_issuer.sql`：重建 `device_pairing_codes`，列 `device_id` 改为 `issuer_id` 并移除对 `devices(id)` 的外键，旧行原样复制。匿名槽位不创建任何设备，`/bootstrap` 的空库判断保持有效。
- 单活码语义不变，但匿名槽位由所有未配对设备共享：任一未配对设备重新生成，会覆盖其他未配对设备尚未使用的码。
- 客户端设置页「配对新设备」不再按配对状态隐藏；三端共用同一 Compose 页面。
- 限流不变：取码按 IP 每分钟 10 次；配对尝试按 IP 每分钟 5 次。

## Considered Options

- **只去掉 UI 门槛，服务端仍要求 Bearer**：未配对设备取码会 401，需求无法实现。
- **为匿名请求创建伪设备行**：污染 `devices` 表，使 `/bootstrap` 的空库判断永久失效，伪设备还会出现在设备数据中。
- **匿名码放内存或独立表**：重启即失效，或需要双源查找、清理与哈希查重，违背「状态都在 SQLite」的既有架构。
- **按 IP 派生匿名槽位**：行数随 IP 无限增长，单活语义割裂；本期不做。

## Consequences

- 安全边界（显式接受）：任何能访问服务器的客户端都能生成匿名配对码并完成配对，等价于开放自助注册；公网明文 HTTP 下可被滥用。IP 限流只能降低刷码速度，不能阻止注册。
- 匿名槽位是共享资源：一个未配对客户端反复取码，会使其他未配对客户端刚拿到的码失效；正常的「取码即用」流程不受影响。
- 路径 `/api/v1/devices/me/pairing-code` 保留 `me` 字样以兼容既有客户端、测试与日志口径，鉴权语义以本 ADR 为准。
- 升级迁移保留旧码与使用状态，已配对设备不受影响；新码统一写入 `issuer_id`。
- 若后续收紧为「仅未配对设备匿名」或引入 per-IP 槽位、设备撤销，需要新的 ADR。
