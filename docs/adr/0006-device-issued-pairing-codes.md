# 配对码改由已配对设备生成，并允许空库自助初始化

**Status**: accepted

**Date**: 2026-11-18

## Context

v1.0.0 原设计要求配对码只由服务端管理接口生成（`POST /api/v1/admin/pairing-codes`，需 `X-Admin-Token`），并在启动时自动生成一个码打印到容器日志。实际的添加设备流程因此不可自助：已配对设备没有取码入口，用户必须登录服务器查看日志或持有管理令牌调用管理接口，这与“跨设备文本中转”的产品定位不符。

用户于 2026-11-18 明确决策：参考微信输入法的跨设备连接体验，每台设备按需生成自己的临时配对码，服务端只负责校验与落库，不再由服务端发码；首次部署的空数据库不做额外门禁，由首台设备自助初始化。该改造纳入 v1.0.0 收尾，而不是推迟到 v1.1。当前仓库尚未打 `v1.0.0` tag，契约改写不会破坏已发布客户端。

## Decision

- 新增设备接口 `POST /api/v1/devices/me/pairing-code`（设备 Bearer 认证）：已配对设备生成 6 位数字码，响应 `201 {code, expiresAt}`。
  - TTL 600 秒，一次性使用；每台设备同一时间只有一个有效码，重新生成即覆盖旧码并使其立即失效。
  - 服务端只保存 `SHA-256(code)`，明文只在生成响应返回一次；不打印、不落盘、不进入 URL。
  - 客户端只在内存中保留明文，设置页弹层关闭即销毁。
- `POST /api/v1/pair` 语义不变：新设备用码换取设备令牌，成功后加入唯一用户空间并触发既有全量同步；码按哈希查找与消费。
- 新增公开接口 `POST /api/v1/bootstrap`：仅当 `devices` 表为空时创建首台设备并返回与配对同形的 `deviceId/token/deviceName`；已有设备返回 409 `ALREADY_INITIALIZED`。空库判断与写入在同一写事务内完成。
- 删除管理码接口、`AdminService`、启动自动发码与 `[PAIRING-CODE]` 日志、`ADMIN_TOKEN` 配置及校验、旧 `pairing_codes` 表。
- 迁移 `V002__device_pairing_codes.sql` 新增 `device_pairing_codes`（`device_id` 主键、`code_hash` 唯一、`expires_at` 索引）并删除 `pairing_codes`；已配对设备不受影响。

## Considered Options

- **保留管理接口，只加设备取码**：两套发码路径并存，管理令牌仍需部署与轮换，运维复杂度不降反升。
- **服务端为每台设备长期保存固定配对码**：码长期有效会放大暴力枚举与泄露风险，也违背一次性原则。
- **长码或二维码**：更强，但需要相机权限或更复杂的输入体验，与 v1.0.0 的范围和权限约束冲突。
- **空库初始化加部署密钥门禁**：能消除抢占窗口，但需要再引入一套部署秘密与客户端输入项；用户明确选择不做门禁。
- **把改造推迟到 v1.1**：v1.0.0 尚未发布，此时改契约成本最低；推迟会让首个版本带着不可自助的配对流程交付。

## Consequences

- 配对流程变为：新部署先初始化首台设备；之后任一已配对设备在设置页生成码；新设备输入码完成配对。三端 UI、iOS UITest、官网自建说明与部署文档必须同步。
- 安全边界（显式接受）：
  - 6 位码空间为 10^6；在 10 分钟有效期内，按 5 次/分钟/IP 最多尝试 50 次，单码命中概率约 5×10^-5。码哈希与单活码限制进一步降低泄露面。
  - 公网明文 HTTP 下，配对码与设备令牌可被链路窃听；该风险与 ADR-0003 的既有边界一致，仅限个人学习与可信网络。
  - 空库初始化不做门禁：从部署完成到首次初始化之间存在被他人抢先取得首台设备令牌的窗口。部署流程必须在服务可用后立即初始化；一旦被抢占，只能停止服务、重置数据库后重新初始化。
  - 没有失败锁定计数，只有 IP 限流；超出 v1.0.0 范围。
- 数据库迁移会删除旧 `pairing_codes` 表；升级时任何未使用的旧码作废，已配对设备与历史数据不受影响。
- 后续若引入 TLS、长码、二维码、失败锁定或设备撤销，需要新的 ADR，不在本版追加。
