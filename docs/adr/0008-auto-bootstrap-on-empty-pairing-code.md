# 首台设备留空配对码自动认领空库

**Status**: accepted

**Date**: 2026-11-19

## Context

v1.0.0 配对页在「配对」按钮下方提供次要入口「初始化此服务器（首次部署）」：点击后二次确认，再调用 `POST /api/v1/bootstrap` 创建首台设备。该入口来自 ADR-0006：服务端启动不创建设备、不打印配对码，首台设备必须主动认领令牌。实际使用中，这个独立入口把「配对」拆成两个动作，首次部署多一次点击与二次确认，用户判定其冗余。

2026-11-19 用户明确决策：删除手动初始化入口与二次确认，改为首台设备首次连接时自动认领——配对码留空点击「配对」即自动调用 `/bootstrap`。服务端 HTTP 契约与启动行为完全不变；本 ADR 只改变客户端触发方式。

## Decision

- 配对页只保留一个「配对」按钮：
  - 配对码留空：调用 `POST /api/v1/bootstrap`，成功后保存凭据并进入已配对状态。
  - 配对码恰好 6 位：调用 `POST /api/v1/pair`，语义与错误映射不变。
  - 配对码 1–5 位：按钮禁用，不发起请求。
- 删除「初始化此服务器（首次部署）」入口、二次确认对话框、`PairingViewModel.initialize()`、`PairingUiState.isInitializing/canInitialize` 与 5 条 `pair_init_*` 文案；初始化与配对共用提交中状态、429 冷却、错误映射与会话重建事件。
- 服务器已有设备时，空码提交返回 409 `ALREADY_INITIALIZED`，复用既有文案「服务器已初始化，请输入任意设备生成的配对码」。
- 服务端路由、`PairingService`、迁移、限流、启动日志零改动；iOS UITest 仍直接调用 `/bootstrap`。

## Considered Options

- **服务端启动时创建首台设备并交付令牌**：启动时没有设备在场，明文令牌只能写入日志、服务器文件或环境变量。日志违反「令牌与配对码不进入日志」，文件 / 环境变量把令牌交付变成新的部署秘密通道；同时启动即建行会让 `devices` 空库判断永久失效，与 ADR-0006 的 `/bootstrap` 语义冲突。
- **页面加载即自动初始化**：打开配对页（甚至只是查看或切换语言）就会写库，无用户意图，可能误占他人的空库；离线或地址错误时产生无意义请求与错误噪声。
- **保留手动入口（现状）**：多一次点击与二次确认；用户已判定冗余。
- **新增「首次部署」显式勾选**：仍是双入口，新增状态与错误路径，收益不抵成本。

## Consequences

- 空库初始化与配对收敛为同一按钮；客户端少一个入口、5 条文案与一组状态字段。
- 空库抢占窗口仍然存在，与现有公开 `/bootstrap` 的暴露等价；ADR-0006 已显式接受，部署文档继续要求上线后立即用首台设备完成初始化。
- 空码与错码无法区分：已初始化服务器上留空提交只会得到 409 引导，不会自动回退为 `pair`；提示文案必须同时覆盖「首次部署」与「已有设备」两种情形。
- 限流差异保留：`/bootstrap` 3 次 / 分钟 / IP、`/pair` 5 次 / 分钟 / IP；客户端共用同一冷却实现。
- 若后续需要「确认即将占用空库」的显式确认，需要新的 ADR。
